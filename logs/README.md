# Logging

## Overview

The Ubuntu SQL Server project uses logs to monitor services, troubleshoot problems, review automated tasks, and track applications running on U-Server.

Logs may be generated by the operating system, PostgreSQL, systemd services, Docker containers, the Go Agent, the Django Web Dashboard, backup processes, and other services.

This document provides a central reference for locating, viewing, and understanding project logs.

## Purpose

Logging helps with:

- Troubleshooting application and service failures
- Monitoring server activity
- Reviewing automated tasks
- Checking application startup and shutdown
- Reviewing database problems
- Tracking backup operations
- Monitoring Docker containers
- Investigating health monitoring problems
- Reviewing notification failures

Logs should provide useful information without exposing passwords, tokens, API keys, or other sensitive information.

---

## Systemd Logs

Services managed by systemd normally write their output to the system journal.

Logs can be viewed using `journalctl`.

### View Logs for a Service

```bash
journalctl -u <service-name>
```

### View Recent Logs

```bash
journalctl -u <service-name> -n 50 --no-pager
```

### Follow Logs in Real Time

```bash
journalctl -u <service-name> -f
```

Press `Ctrl+C` to stop following the log.

### View Logs Since the Current Boot

```bash
journalctl -u <service-name> -b
```

## Go Agent Logs

The Go Agent performs server inventory collection, operating system detection, hardware detection, network collection, health monitoring, database updates, and health alert processing.

The Go Agent runs through:

```text
ubuntu-sql-agent.service
```

### View Agent Logs

```bash
journalctl -u ubuntu-sql-agent.service
```

### View Recent Agent Logs

```bash
journalctl -u ubuntu-sql-agent.service -n 50 --no-pager
```

### Follow Agent Logs

```bash
journalctl -u ubuntu-sql-agent.service -f
```

Press `Ctrl+C` when finished.

### Information Recorded

Go Agent logs may contain information about:

- Server inventory updates
- Operating system information
- Hardware components
- Network interfaces
- System health
- Health check IDs
- Database connection problems
- Alert events
- Notification delivery
- Agent execution failures

A normal health section may contain information similar to:

```text
System Health
---
1-Minute Load Average: 0.01
Memory Usage: 12.13%
Disk Usage: 8.13%
Uptime: 122.42 hours
Overall Status: HEALTHY
Health check saved successfully.
Health check ID: 26
```

Values will change depending on the current state of the server.

### Go Agent Service Behavior

The Go Agent service runs as a task rather than a continuously running process.

The agent performs its server refresh and then exits.

After a successful run, systemd may report:

```text
ubuntu-sql-agent.service: Deactivated successfully.
Finished ubuntu-sql-agent.service - Ubuntu SQL Server Go Agent.
```

This is normal and does not mean the agent failed.

A successful refresh should normally include messages showing that server information was updated, a health check was saved, and the refresh completed.

## PostgreSQL Logs

PostgreSQL maintains database logs that can be used to investigate database and connection problems.

### Check PostgreSQL

```bash
sudo systemctl status postgresql
```

### Check PostgreSQL Clusters

```bash
pg_lsclusters
```

The PostgreSQL 16 main cluster log is normally located at:

```text
/var/log/postgresql/postgresql-16-main.log
```

### View Recent PostgreSQL Logs

```bash
sudo tail -n 50 /var/log/postgresql/postgresql-16-main.log
```

### Follow PostgreSQL Logs

```bash
sudo tail -f /var/log/postgresql/postgresql-16-main.log
```

Press `Ctrl+C` when finished.

PostgreSQL logs are useful for investigating:

- Connection failures
- Authentication failures
- Permission problems
- SQL errors
- Database startup problems
- Unexpected database shutdowns
- Application database connection failures

## Django Web Dashboard Logs

The Django Web Dashboard may produce logs related to:

- Application startup
- Database connections
- HTTP requests
- Application errors
- Django configuration
- Database migrations
- Database queries

When Django is started manually, its output is displayed directly in the terminal.

For example:

```bash
python manage.py runserver
```

If the dashboard is managed through systemd or another application server in the future, its logs should be reviewed through that service.

Database connection errors in the dashboard may also require checking PostgreSQL logs.

## Minecraft Backup Logs

Minecraft backups are managed using a systemd service and timer.

### Check the Backup Timer

```bash
systemctl status minecraft-backup.timer
```

### View Scheduled Backup Times

```bash
systemctl list-timers --all | grep minecraft-backup
```

### View Backup Logs

```bash
journalctl -u minecraft-backup.service
```

### View Recent Backup Logs

```bash
journalctl -u minecraft-backup.service -n 50 --no-pager
```

Backup logs can be used to confirm that:

- World data was prepared for backup
- Automatic saving was temporarily disabled
- World data was flushed to disk
- The backup archive was created
- Automatic saving was re-enabled
- The backup completed successfully

Backup archives themselves should not be committed to Git.

## Health Monitoring

The Go Agent records system health information in PostgreSQL.

Health checks currently include information such as:

- 1-minute load average
- Memory usage
- Disk usage
- Uptime
- Overall health status

The monitoring system uses three health states:

```text
HEALTHY
WARNING
CRITICAL
```

Each health check is stored in the database and receives a health check ID.

Health history can be used to review how the condition of U-Server changes over time.

---

## Alert Event Logging

Health status changes can create alert events.

Alert events are stored in:

```text
server_management.alert_events
```

The table records information including:

- Server ID
- Previous health status
- New health status
- Alert title
- Alert message
- Creation time

Examples of possible health transitions include:

```text
HEALTHY -> WARNING
HEALTHY -> CRITICAL
WARNING -> CRITICAL
WARNING -> HEALTHY
CRITICAL -> HEALTHY
```

A recovery event may appear as:

```text
Previous Status: WARNING
New Status: HEALTHY
Title: U-Server Recovered
```

Alert events provide a permanent database record of important changes in server health.

---

## Notification Logging

The Go Agent can send server health notifications through ntfy.

Notifications may be generated when:

- The server enters a WARNING state
- The server enters a CRITICAL state
- The server recovers to HEALTHY

Successful notification delivery may appear in the Go Agent output as:

```text
Notification sent successfully.
```

Notification failures should also appear in the agent output or systemd journal.

Private notification topic names and other sensitive notification configuration should not be written into public documentation or committed to Git.

## Backup and Restore Logging

Backup and restore operations should provide enough output to determine whether an operation completed successfully.

Useful backup and restore information includes:

- Operation start time
- Backup source
- Backup destination
- Archive creation
- Restore source
- Service shutdown
- Data extraction
- Service restart
- Completion status

After restoring data, affected services should be checked to make sure they returned to a healthy state.

## Firewall Troubleshooting

A service can be running correctly while still being unreachable because of firewall rules.

The current UFW configuration can be viewed with:

```bash
sudo ufw status numbered
```

When a running service cannot be reached, check:

1. Whether the service is running
2. Whether the service is listening on the expected port
3. Whether UFW allows the required connection
4. Whether Docker exposes the required port
5. Whether the client can reach U-Server
6. Whether the application is listening on the correct network interface

Firewall rules should only expose services that need network access.

---

## Checking Listening Ports

Listening TCP ports can be checked with:

```bash
sudo ss -lntp
```

A specific port can be checked with:

```bash
sudo ss -lntp | grep <port>
```

This can help determine whether an application is actually listening when troubleshooting a connection problem.

## General Troubleshooting Process

When a service fails or becomes unavailable:

1. Check the service status.
2. Review recent logs.
3. Identify the first meaningful error.
4. Check related services.
5. Verify database connectivity if required.
6. Check network connectivity.
7. Check firewall rules.
8. Verify environment variables and configuration.
9. Restart only the affected service when possible.
10. Review the logs again after the restart.
11. Confirm the service returned to a healthy state.

Avoid changing several settings at the same time.

Making one change at a time makes it easier to determine what caused the problem and what fixed it.

## Sensitive Information

Logs must be handled carefully because application output can accidentally contain sensitive information.

Do not intentionally log:

- Passwords
- Database passwords
- API keys
- Access tokens
- Private keys
- Authentication headers
- Secret environment variables
- Private notification topics

Logs should be reviewed before they are:

- Shared publicly
- Posted to GitHub
- Included in bug reports
- Sent to another person
- Added to documentation

If sensitive information is accidentally exposed, the affected credential or secret should be replaced.

---

## Git Policy

Runtime logs should not normally be committed to the repository.

The project `.gitignore` excludes files ending in:

```text
*.log
```

Application runtime directories containing logs should also be excluded when appropriate.

Documentation about logging can still be stored in this directory.

---

## Log Retention

Logs should be kept long enough to support troubleshooting without allowing unnecessary files to consume server storage.

System-managed services such as systemd and PostgreSQL may manage their own log rotation and retention.

Application-specific retention policies can be added as the project grows.

Old logs should only be removed after confirming they are no longer needed for troubleshooting or recovery.
